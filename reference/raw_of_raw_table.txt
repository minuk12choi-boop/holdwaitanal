================================================================================
raw_of_raw_table.txt
  Spotfire 로딩용 Oracle 원본(raw) 테이블 조회 쿼리
================================================================================

[목적]
  기존: bdq -> datalake(Impala) 직접 조회
  변경: Spotfire 로 원본 DB 조회 -> S3 Drive 적재 -> python 이 S3 에서 읽어 전처리

  따라서 여기에는 **전처리가 전혀 없는 생테이블 조회**만 둔다.
  결합/윈도우/집계는 전부 python(build_f3.py, get_move.py)이 그대로 담당한다.

[원칙]
  - Oracle 도 PK 가 없어 WHERE 를 많이 건다고 빨라지지 않는다.
    현재 Impala 최적화 버전에서 유지 중인 조건(라인 한정, owner, TrackOut 등)만 옮긴다.
  - 컬럼은 python 이 실제로 쓰는 것만 SELECT 한다(전송량 절감).
  - 날짜/숫자 변환, NULL 처리, 최신건 선별은 여기서 하지 않는다.
    (Impala 버전의 CAST / TO_TIMESTAMP / 윈도우 선별은 python 단으로 이관)
  - S3 에 올릴 때 아래 [S3 파일명] 을 그대로 쓰면 python 쪽 매핑이 단순해진다.

[대상 라인] PFR1(=smicdc_p3nrd), KFR7(=smicdc_nrdk)

-- 8) pfr1_step_path : smicdc_p3nrd.mc_lot_step_path
--    현재 Impala 버전과 동일하게 mc_lot(Active/Hold) 조인으로 행을 줄인다.
--    delay_step_type S/Y 는 de_rank 누적 계산에 필요해 위치와 무관하게 남긴다.
--------------------------------------------------------------------------------
SELECT p.lot_id,
       p.order_seq,
       p.proc_id,
       p.step_seq,
       p.step_desc,
       p.step_level,
       p.step_skip_yn,
       p.delay_step_type,
       p.delay_time_mins,
       p.layer_id,
       p.eqp_type,
       p.eqp_group_id,
       p.recipe_id,
       p.ext_1st_vals,
       p.tkin_type_detail
FROM   smicdc_p3nrd.mc_lot_step_path p,
       (SELECT DISTINCT lot_id, order_seq
        FROM   smicdc_p3nrd.mc_lot
        WHERE  lot_status_seg IN ('Active', 'Hold')) c
WHERE  p.lot_id = c.lot_id
  AND  (p.order_seq >= c.order_seq
        OR p.delay_step_type IN ('S', 'Y'))
;

-- 15) move : MI_LOT_TRANSN_HIST_V
--     MOVE = TrackOut 매수. lot_type 은 PP/PB/PG 만.
--     line_id 는 cur/sys 합집합이라 sys_line_id 조건을 함께 건다.
--     기간은 Spotfire 파라미터로 바꿔 쓴다(아래는 최근 3일).
--------------------------------------------------------------------------------
SELECT sys_line_id,
       line_id,
       current_line_id      AS cur_line_id,
       lot_id,
       lot_type,
       component_qty        AS move,
       ppid,
       process_eqp_id,
       process_id,
       step_seq,
       step_desc,
       eqp_type,
       recent_tkout_time,
       tkin_date,
       process_start_date,
       process_finish_date,
       lot_transn_time
FROM   MI_LOT_TRANSN_HIST_V
WHERE  line_id     IN ('KFR7', 'PFR1')
  AND  sys_line_id IN ('KFR7', 'PFR1')
  AND  lot_transn_type = 'TrackOut'
  AND  lot_type IN ('PP', 'PB', 'PG')
  AND  lot_transn_time >= TO_CHAR(SYSDATE - 3, 'YYYYMMDD HH24MISS')
;

  ※ 최초 3개월 백필 시에는 마지막 조건만 바꾼다.
       AND lot_transn_time >= TO_CHAR(TRUNC(ADD_MONTHS(SYSDATE, -3), 'MM'),
                                      'YYYYMMDD HH24MISS')
  ※ lot_transn_time 이 DATE 타입이면 TO_CHAR 없이 비교한다.
       AND lot_transn_time >= SYSDATE - 3


================================================================================
3. 확인필요
================================================================================

(1) PFR1 의 fa_object4
    지금 python 은 KFR7 만 materialworkstatus 를 조인하고 PFR1 은 NULL 로 채운다.
    매칭표에 PFR1 쪽 테이블도 있으므로 쿼리는 함께 넣어 두었다.
    PFR1 에도 값을 붙일지 결정 필요. 붙이면 기존 결과와 값이 달라진다.

(2) memmss.fab_issue_lot 의 version_desc
    Impala 적재본에서는 스냅샷 ID 였고, 최신 version_desc 로 좁힌 뒤
    status_seq <> '2' 를 적용했다.
    - Oracle 원본이 **현재값만** 갖는 구조면: version_desc 불필요. 지금 쿼리 그대로.
    - Oracle 원본도 **누적 스냅샷**이면: SELECT 에 version_desc 를 넣고
      python 에서 최신 선별을 유지해야 한다. 넣지 않으면 조치완료된 옛 건이
      되살아난다.
    첫 적재 후 (lot_id, step_seq, item_type) 중복 여부로 판별 가능하다.

(3) MI_LOT_TRANSN_HIST_V 의 스키마 접두
    매칭표에 스키마 없이 뷰 이름만 있다. 접근에 스키마가 필요하면 앞에 붙일 것.

(4) 날짜 계열 컬럼 타입
    Impala 에서는 STRING 이라 python 이 숫자만 뽑아 파싱한다
    (mc_lot 의 start_date / last_tkout_date / step_arrive_date / last_event_date,
     equipment 의 eqp_status_change_time, move 의 lot_transn_time).
    Oracle 에서 DATE 로 오면 python 파싱을 손봐야 한다. 첫 적재 후 확인 필요.

(5) step_path 조인의 Oracle 성능
    Impala 에서는 이 조인이 전송량을 크게 줄였다(683만 -> 457만). Oracle 에서
    느리다면 조인을 빼고 생테이블로 받아 python 에서 거르는 쪽으로 되돌린다.
