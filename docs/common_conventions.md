# Fab Flow Monitor — 공용 규칙

이 문서는 `build_f3.py`, `get_move.py`, 웹 사이트 전반에 **공통으로 적용되는 정의**를
모아둔 것이다. 새 지표나 화면을 만들 때 여기 정의를 그대로 따른다.

---

## 1. 업무일 (biz_date)

Fab 의 하루는 **22:00 시작 ~ 다음날 22:00 종료** 다.

```
2026-08-10 22:00:00  이상  ~  2026-08-11 22:00:00  미만   →  biz_date = 2026-08-11
```

즉 실행 시각이 22:00 이상이면 **다음 날짜**, 미만이면 **당일 날짜**가 업무일이다.

```python
def biz_date(ts):
    return (ts + timedelta(days=1)).date() if ts.hour >= 22 else ts.date()
```

## 2. Shift

| Shift | 기준 시각 | 구간 | 비고 |
|---|---|---|---|
| `GY` | 22:00 | 22:00 ~ 06:00 | **업무일의 첫 shift** |
| `DAY` | 06:00 | 06:00 ~ 14:00 | |
| `SW` | 14:00 | 14:00 ~ 22:00 | 업무일의 마지막 shift |

`biz_date = 2026-08-11` 의 shift 순서는 다음과 같다.

```
GY  (08-10 22:00)  →  DAY (08-11 06:00)  →  SW (08-11 14:00)
```

### 하루의 대표값

특별히 shift 를 지정해 조회하지 않는 한, **하루의 대표 표현은 `GY`(22:00) 데이터**다.

### Shift 배정 규칙 (스냅샷 적재)

스케줄러 실행 시각은 기준 시각과 정확히 일치하지 않는다. 그래서 **기준 시각에
가장 가까운 스냅샷**을 그 shift 의 데이터로 삼는다.

- 실시간 테이블은 **최근 2벌**의 스냅샷을 보관한다 (화면에는 최신 1벌만 노출).
- 매 실행마다 직전 shift 기준 시각과의 시간차(`dist_sec`)를 계산해,
  기존에 적재된 것보다 **더 가까운 스냅샷이면 교체**한다.
- 예) 21:50 실행 후 22:50 실행 → 22:00 기준으로 21:50(10분)이 22:50(50분)보다
  가까우므로 21:50 스냅샷이 `GY` 로 남는다.
- 스냅샷의 shift 라벨은 **그 shift 가 시작되는 시점** 기준이다.
  22:00 스냅샷 = 다음 업무일의 `GY`, 06:00 = `DAY`, 14:00 = `SW`.

이 방식은 다음 실행 시각을 몰라도 되고, 몇 번을 재실행해도 결과가 같다(멱등).

## 3. MOVE

### 정의

**MOVE = TrackOut 된 wafer 매수(qty)**. 건수가 아니라 매수다.

### 대상 Lot Type

```
lot_type IN ('PP', 'PB', 'PG')
```

이 세 종류만 생산성으로 인정한다. **다른 lot type 은 MOVE 에서 제외**한다.

### 집계 구간

`build_f3.py` 의 스냅샷 적재 시각을 `n` 이라 할 때,

| 단위 | 구간 |
|---|---|
| Shift | 그 shift 의 **실제 근무 구간** (GY 22~06, DAY 06~14, SW 14~22) |
| 일 | 업무일 전체 22:00~22:00 (= 3개 shift 의 합) |

### 스냅샷과 MOVE 의 짝 (W/T 계산)

f3 스냅샷과 MOVE 는 **같은 `(업무일, shift)` 라벨끼리 그대로 짝**이 된다.

| shift | f3 스냅샷 시각 (재공) | MOVE 구간 |
|---|---|---|
| `GY` | `(D-1) 22:00` | `(D-1) 22:00 ~ D 06:00` |
| `DAY` | `D 06:00` | `D 06:00 ~ D 14:00` |
| `SW` | `D 14:00` | `D 14:00 ~ D 22:00` |

```
W/T(D, S) = MOVE(D, S) ÷ 재공(D, S 스냅샷)
```

**분모는 그 조가 시작할 때의 재공, 분자는 그 조가 낸 MOVE** 다.
스냅샷은 shift 가 시작되는 시점으로 라벨링한다(`db_common.snapshot_shift`).

일 단위는 `(D, GY)` 스냅샷(= `(D-1) 22:00`, 업무일 시작 재공)과
업무일 `D` 전체 MOVE 를 쓴다.

적재 초기처럼 그 업무일에 `GY` 가 아직 없으면 **`DAY` → `SW` 순으로 대체**한다.
없는 날을 통째로 비우는 것보다 낫다.

## 4. W/T (WIP Turn)

```
W/T = MOVE(매) ÷ 재공(매)
```

**분모의 재공도 `lot_type IN ('PP','PB','PG')` 의 매수만 센다.** MOVE 가 특정
lot type 에 한정된 지표이므로 분모도 같은 모집단이어야 한다.

### 예시

20매짜리 LOT 이 하루에 48 MOVE 를 냈다면

```
W/T = 48 / 20 = 2.4
```

### Line 단위

```
LINE W/T = LINE 전체 MOVE ÷ LINE 전체 재공(매)
```

lot 별 W/T 의 평균이 **아니다**. 분자·분모를 각각 합산한 뒤 나눈다.

### 분자·분모의 시간 정합

W/T 의 분모(재공)는 스냅샷 시점 값이고 분자(MOVE)는 구간 누적이다.
**스냅샷 시각 `n` 과 MOVE 구간의 끝이 일치**해야 한다.

- Shift W/T : 분모 = `n` 시점 재공, 분자 = `n-8h ~ n` MOVE
- 일 W/T : 분모 = `n` 시점 재공, 분자 = `n-24h ~ n` MOVE

## 5. 테이블 구성

| 테이블 | 용도 | 갱신 방식 |
|---|---|---|
| `f3_live` | 웹 실시간 상세. 최근 2벌 스냅샷 | 매 실행 시 추가, 2벌 초과분 삭제 |
| `f3_history` | shift 단위 누적 상세 | shift 기준 시각에 가장 가까운 스냅샷으로 교체 |
| `f3_history_meta` | 어떤 스냅샷이 어느 shift 로 채택됐는지 | `(biz_date, shift)` 유일 |
| `move_shift` | shift 단위 MOVE 집계 | `(biz_date, shift, sys_line_id)` 교체 |
| `move_daily` | 일 단위 MOVE 집계 | `(biz_date, sys_line_id)` 교체 |

웹은 실시간 조회 시 `f3_live` 의 최신 스냅샷을, 과거 조회 시 `f3_history` 를 본다.

## 5-0. 데이터 조달 경로 (변경)

```
기존  bdq -> datalake(Impala) 직접 조회 -> python 전처리

```

Spotfire 쪽 Oracle 쿼리 8개는 `reference/raw_of_raw_table.txt` 에 있고,
테이블 이름을 그대로 S3 오브젝트 이름으로 쓴다.

| Spotfire 테이블 | S3 오브젝트 |
|---|---|
| `PFR1_KFR7_LOT` | `<prefix>PFR1_KFR7_LOT.pkl` |
| `PFR1_KFR7_MATERIALWORKSTATUS` | 〃 |
| `PFR1_KFR7_STEP_PATH` | 〃 |
| `PFR1_KFR7_TIP` | 〃 |
| `PFR1_KFR7_EQUIPMENT` | 〃 |
| `PFR1_KFR7_EQP_GROUP` | 〃 |
| `PFR1_KFR7_HOLD` | 〃 |
| `PFR1_KFR7_MOVE` | 〃 |

적재는 `getdata/spotfire_s3_export.py` 를 Spotfire 데이터 함수로 등록해 처리한다
(Tools > Register Data Functions, Refresh = Automatic). 분석 파일이 열려 데이터가
새로 로딩될 때마다 자동으로 올라간다.

**주의**: 클라우드(웹) Spotfire 는 서버 Python 을 쓰므로 로컬에 설치한 boto3 가
잡히지 않는다. Spotfire Analyst(설치형)에서 실행해야 한다.

### S3 -> python

`getdata/s3_source.py` 가 S3 의 pkl 을 읽어 DataFrame 으로 돌려준다.
파일로 내려받지 않고 `get_object` + `io.BytesIO` 로 메모리에서 바로 읽는다.
**raw 자체는 DB 에 넣지 않는다.** bdq 로 받던 자리를 그대로 대체할 뿐이고,
DB 에 적재되는 것은 전처리 결과(f3, move)뿐이다.

```
python getdata/s3_source.py --list      S3 오브젝트 목록
python getdata/s3_source.py --peek LOT  한 테이블 미리보기
python getdata/s3_source.py --check     8개 전부 읽어 행수/컬럼 점검
```

Oracle 은 컬럼을 대문자로 주므로 읽는 즉시 소문자로 통일한다
(`LOWER_COLUMNS`). 이후 전처리는 기존 코드 그대로다.

### 원천 전환 스위치

`build_f3.py` / `get_move.py` 상단의 `SOURCE` 한 줄로 바꾼다.

```python
SOURCE = "s3"      # Spotfire 가 올린 raw (현행)
SOURCE = "bdq"     # 기존 bigdataquery 로 Impala 직접 조회 (폴백)
```

전처리·적재·웹은 양쪽이 완전히 동일하다. 바뀌는 것은 원천을 어디서 받느냐뿐이다.

S3 경로에서 달라지는 점 세 가지:
- `fa_object4` 는 datasource 가 달라 별도 파일로 오므로 `(line, lot_id)` 로 붙인다
- `STEP_PATH` / `TIP` 은 두 라인이 한 파일이라 `line` 으로 나눠 쓴다(파일은 1회만 읽음)
- `hold` 는 Oracle 쿼리에서 최신 `version_desc` 선별까지 끝나 별도 조회가 없다

## 6. 적재 주기

| 스크립트 | 주기 | 비고 |
|---|---|---|
| `getdata/build_f3.py` | **22:00 시작, 2시간 간격** | 실시간 갱신 + 06/14/22시분이 shift 로 누적됨 |
| `getdata/get_move.py` | **2시간마다 (build_f3 과 함께)** | 최초 3개월치, 이후 최근 20시간 |

스케줄러에는 `scripts/run_build_f3.bat` **하나만** 등록한다. 이 래퍼가 실행 시각을
보고 shift 기준시각(06/14/22시)일 때 `get_move.py` 까지 이어 돌린다.
`.bat` 은 반드시 작업 스케줄러에 등록해야 동작한다
(자세한 내용은 `docs/scheduler_guide.md`).

`getdata/db_common.py` 는 **실행 대상이 아니다.** 두 스크립트가 함께 쓰는
공용 라이브러리(접속·스키마·업무일/shift 계산·적재)이므로 스케줄러에 등록하지 않는다.

### Windows 작업 스케줄러 설정

작업 폴더를 지정하지 않으면 `C:\Windows\System32` 에서 실행되어 `.env` 와
상대경로가 어긋난다. `scripts/*.bat` 래퍼를 통해 실행한다.

| 항목 | build_f3 | get_move |
|---|---|---|
| 프로그램 | `scripts\run_build_f3.bat` | `scripts\run_get_move.bat` |
| 시작 위치 | 프로젝트 루트 | 프로젝트 루트 |
| 트리거 | 매일 00:00 시작, **1시간 간격** 반복, 기간 1일 | 매일 22:30 |
| 옵션 | "작업이 이미 실행 중이면 새 인스턴스 시작 안 함" | 동일 |

`snapshot_at` 은 **원천 조회를 시작한 시각**으로 기록된다. 따라서 정각에 시작하면
스냅샷도 정각으로 남아 shift 기준시각과 정확히 맞는다.

### 저빈도 테이블 캐시

설비그룹(`SMIMES_MI_EQP_GROUP_LIST`)처럼 하루에 한 번만 바뀌면 충분한 테이블은
**업무일(22시 기준) 단위로 로컬 캐시**한다. `getdata/cache/<name>_<YYYYMMDD>.csv`

- `'OFF'` 설비 제외까지 마친 상태로 저장한다
- 같은 업무일 안에서는 파일에서 읽고, 날짜가 바뀌면 새로 조회한다
- 이전 날짜 캐시는 자동 삭제된다

2시간 간격 실행 기준 하루 12회 중 1회만 실제 조회한다.

### MOVE 초기 적재 범위

3개월 전 날짜가 속한 **달의 1일**부터 채운다.

```
오늘 2026-08-10  →  3개월 전 2026-05-10  →  적재 시작일 2026-05-01
```

### MOVE 증분 적재

2시간마다 돌면서 **최근 20시간**을 받는다. 진행 중인 shift(최대 8h)와 직전
shift(8h)를 덮고도 여유가 있어, 실행이 몇 시간 밀려도 공백이 생기지 않는다.

조회 구간의 시작은 그 시각이 속한 **shift 시작 시각으로 정렬**해 구간이 경계에서
잘리지 않게 한다. 끝은 '지금' 이라 진행 중인 shift 도 부분 집계되며, 다음 실행에서
그 shift 전체로 교체된다.

교체 단위는 **(업무일, shift) 쌍**이다. 업무일 통째로 지우면 같은 업무일의 이미
적재된 다른 shift 가 날아간다. `move_daily` 는 교체 후 `move_shift` 에서 다시
합산해 만든다.

## 7. 차트 규칙

### 시각 속성 (blueprint 준수)

| 속성 | 의미 |
|---|---|
| 색 | **Line** |
| 선 종류 | Lot Type |
| 위치(패널) | 지표 |

Line 간 비교가 설계의 핵심이므로, **모든 차트는 Line 별로 구분해 그린다.**

### MOVE 차트 x축

```
[ 6월  7월  8월 ] │ [ W30  W31  W32  W33 ] │ [ 8/4 8/5 8/6 8/7 8/8 8/9 8/10 ]
     3개월              4주                        7일
```

- **당월·당주 포함**. 진행 중인 구간도 그린다.
- 단위가 바뀌는 지점에 **간극(gap)** 을 둬 구분한다.
- 최근 7일은 당월·당주에도 포함되지만 그대로 둔다. 일별 값을 개별로 보기 위함이다.
- **월/주 값 = 그 기간에 속한 일별 값의 평균** (총합 ÷ 일수가 아님)
  - W/T 도 마찬가지다. 총MOVE/총재공이 아니라 **일별 W/T 의 평균**이다.

### HOLD율 / WAIT성 진행불가율의 분모

**기본은 매수(qty) 기준**이며, 화면 상단 토글로 **Lot 수 기준**으로 전환할 수 있다.

```
HOLD율(매수)  = HOLD 상태 Lot 의 매수 합 ÷ 전체 재공 매수
HOLD율(Lot수) = HOLD 상태 Lot 수      ÷ 전체 재공 Lot 수
```

두 값은 크게 다를 수 있다. 매수가 큰 Lot 이 몰려서 HOLD 면 매수 기준이 높게,
소량 Lot 이 여러 건 걸리면 Lot 수 기준이 높게 나온다.
**어느 기준으로 본 값인지 항상 함께 표기**한다(패널 헤더에 표시).

MOVE / W/T / 재공은 정의상 매수 기준이므로 토글의 영향을 받지 않는다.

### 출력 컬럼이 늘어났을 때

`SUMMARY_OUTPUT_COLUMNS` 에 컬럼을 추가하면 `f3_live` / `f3_history` 스키마도
따라가야 한다. `CREATE TABLE IF NOT EXISTS` 는 기존 테이블을 건드리지 않으므로
`db_common.add_missing_columns()` 가 `ALTER TABLE` 로 보강한다.

```
python getdata/db_common.py --init
```

기존 데이터는 그대로 두고 없는 컬럼만 추가된다(기존 행은 NULL).
수동으로 하려면 `getdata/migrate_add_columns.sql` 참조.

### 날짜 컬럼 타입

원천마다 타입이 다르다. Oracle 쿼리에서 `TO_DATE` 로 변환한 컬럼은 datetime 으로,
변환하지 않은 컬럼은 `'YYYYMMDD HHMMSS...'` 문자열로 온다.

python 은 **`db_common.to_datetime()`** 하나로 받는다. 이미 datetime 이면 그대로
두고, 문자열이면 숫자만 뽑아 14자리로 파싱한다(ISO 문자열도 폴백 처리).

```python
d["tkout_date"] = DB.to_datetime(d["tkout_date"])
```

DuckDB 쪽 `parsed_ts()` 도 `TRY_STRPTIME` + `TRY_CAST` 조합이라 양쪽을 받는다.
따라서 Oracle 쿼리에서 날짜 변환을 추가하거나 빼도 python 을 고칠 필요가 없다.

### 경과일 컬럼

f3 는 네 가지 경과일을 담는다. 모두 `현재시각 - 기준시각` 을 일 단위 소수 1자리로.

| 컬럼 | 기준 |
|---|---|
| `투입경과_일` | `start_date` |
| `마지막이벤트경과_일` | `last_event_date` |
| `스텝도착경과_일` | `step_arrive_date` |
| `마지막작업경과_일` | `last_tkout_date` (마지막 TrackOut) |

`마지막작업경과_일` 은 "실제로 설비를 마지막으로 빠져나온 뒤 얼마나 지났는가"라
정체 판정에 가장 직접적이다. 이벤트 경과는 상태 변경만으로도 갱신되므로 다르다.

### 표기 자릿수

| 지표 | 자릿수 |
|---|---|
| MOVE | 정수 |
| 재공 | 정수 |
| W/T | 소수 1자리 |
| HOLD율 / WAIT성 진행불가율 | 소수 1자리 (%) |

월/주 평균도 같은 자릿수로 맞춘다. 화면에는 산식을 표기하지 않는다.

### 차트 값 레이블

점 위에 값을 직접 표기한다. 좁은 패널에 맞춰 축약하되, **커서를 올리면 항상
원래 값**이 보인다.

| 지표 | 레이블 | 툴팁 |
|---|---|---|
| MOVE / 재공 | 1000 단위 + 소수 1자리 (`13.3k`) | `13,300 매` |
| W/T | 소수 1자리 (`2.4`) | `2.4 매/매` |
| HOLD율 / WAIT성 진행불가율 | 정수 (`33`) | `33.3 %` |

### FAB현황 summary 뷰 순서

```
라인 토글 (단일 선택, 기본 NRD-K)
  재공 뷰       LOT / 매 + lot_type 구성
  status 뷰     원차트 + 선택 정보
  W/T 분포 뷰   WT=0 이 맨 위, 아래로 갈수록 정상
  원인 분석 뷰   대분류 > 소분류
```

좌측이 summary(카드 1개 폭), 우측 나머지가 드릴다운이다.

### 원인 대분류 / 소분류

3단계다. 대분류 > 중분류 > 소분류. 겹치면 위에서부터 하나에만 귀속한다.

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| Hold | — | hold 유형 (기준정보) |
| Wait성 진행불가 | 설비이슈 | EQP ID (상위 N) |
| | TIP | EQP ID (상위 N) |
| | FTP | FTP 유형 (기준정보) |
| | 예약제외 | 예약제외 유형 (기준정보) |
| | 가상스텝 대기 | — |
| Bottleneck | — | EQP ID (상위 N) |

- **Bottleneck** 은 `lot_status = 'WAIT'` 인 LOT 만 센다(진행은 가능하나 대기).
- **Hold** 는 `lot_status = 'HOLD'` 또는 hold 값이 있는 LOT.
- 소분류가 설비인 경우 설비그룹 n개면 각 설비에 `1/n` 로 나눠 계상한다.
- 화면은 **차트**로 파고들고, 말단에서 우측 **드릴다운 표**로 원자료를 본다.
  분류 로직(`classify_lot`)을 요약과 드릴다운이 공유해 값이 어긋나지 않는다.

**가상스텝 대기** = `recipe_id` / `step_seq` / `step_desc` 중 하나에 `WAIT` 이
포함된 LOT. Wait성 진행불가의 중분류다.

### lot_type 기본 선택

FAB현황의 lot_type 필터 기본값은 **PP + PG** 다. 사용자가 바꾸면 그 선택이
브라우저에 저장되어 라인이나 뷰를 바꿔도 유지된다.

hold / exception / ftp 의 유형은 아직 정립 전이라 `기준정보` 화면에서 키워드 →
유형 규칙을 등록해 쓴다. 규칙이 없으면 사유 원문이 그대로 유형이 된다.

### 화면 구성

```
┌──────────────────────────────────────────┐
│ 상단 메뉴바                                │
├──────────────────────────────────────────┤
│ 현황 카드  NRD │ NRD-P │ NRD-K │ NRD-V     │  ← 현재 단면(f3_live)
├──────────────────────────────────────────┤
│ FlowStack (추이)        │ 상세             │
└──────────────────────────────────────────┘
```

### 라인 표기

| 화면 표기 | 실제 코드 |
|---|---|
| NRD | KFR4 |
| NRD-P | PFR1 |
| NRD-K | KFR7 |
| NRD-V | KFR6 |

데이터가 없는 라인은 카드를 반투명 처리하고 가운데에 **개발중** 을 띄운다.

### lot_status 색

| 상태 | 색 |
|---|---|
| `RUN` | 파랑 `#2563EB` |
| `WAIT` | 초록 `#16A34A` |
| `HOLD` | 빨강 `#DC2626` |
| `WAIT(진행불가)` | 노랑 `#EAB308` |

도넛 가운데 기본값은 **HOLD + WAIT(진행불가)** 비율이다. 조각이나 범례를 누르면
그 상태의 `%` / `LOT 수` / `매수` 로 바뀌고, 다시 누르면 기본값으로 돌아온다.

### 대기 LOT 상위 설비 5

현스텝의 `eqpgroup` 을 설비 단위로 펼쳐, `lot_status` 가
`WAIT` 또는 `WAIT(진행불가)` 인 LOT 을 센다. `HOLD` 는 설비 대기가 아니므로 제외.

상위 5는 **기준(LOT / 매)마다 따로 뽑는다.** 소량 LOT 여러 건이 걸린 설비와
대량 LOT 소수가 걸린 설비는 순위가 뒤집히므로, 같은 5개를 재정렬하면 안 된다.
화면 기본값은 **매 기준**이다.

**설비그룹이 n개 설비로 엮여 있으면 각 설비에 `1/n` LOT, `1/n` 매로 나눠 계상한다.**
모든 설비에 1랏씩 계상하면 합계가 실제 대기량보다 부풀려진다.

```
25매 LOT 1건이 설비 4개 그룹에서 대기
  -> 설비당 0.25 LOT / 6.25 매
설비 1개 그룹이면
  -> 1.00 LOT / 25 매
```

### 카드의 lot_type 토글

카드 최상단에 **라인 전체 재공(LOT 수 / 매수)** 을 표기하고, 그 옆 토글로
lot_type 을 고른다. `전체` 가 기본이며 선택하면 **카드 전체**(재공 수치,
도넛, 상위 설비)가 해당 lot_type 기준으로 다시 그려진다.

### lot_type 정렬

```
PP → PB → PG → EG → (그 외 오름차순)
```

### Low WT 분석

WT 는 lot 단위로 계산한다. `move_lot`(lot 단위 MOVE) ÷ 재공 매수.
**MOVE 기록이 없으면 WT = 0** 이다. `last_tkout_date` 는 쓰지 않는다
(WT=0 뿐 아니라 저조 WT 구간까지 봐야 하므로).

- 기준은 Dropdown 으로 고른다. 기본 `WT = 0`, 그 외 `WT ≤ 0.5`, `WT ≤ 1.0`
- 기준을 넓혀도 **구간은 합치지 않는다**: `WT=0` / `0<WT≤0.5` / `0.5<WT≤1.0`
- 열은 `전체 | GY | DAY | SW`. **전체는 shift 합이 아니라 unique lot** 기준
  (업무일 대표 스냅샷의 lot + 하루 전체 MOVE)
- Lot 수와 **Low WT율**(분모 = 그 구간의 분석 대상 lot)을 함께 표시

#### 원인 대분류와 우선순위

겹치면 **위에서부터 하나에만** 귀속한다. 중복 카운트 없음.

| 순위 | 대분류 | 판정 |
|---|---|---|
| 1 | Hold | `hold` 값 존재 |
| 2 | Wait성 진행불가 | `exception` 또는 `ftp` 존재 |
| 3 | 설비 | `down` 존재 (DOWN / PM / LOCAL) |
| 4 | TIP | `tip` 존재 (PREVENT) |
| 5 | 기타/미분류 | 위 어디에도 없음 |

```
Hold + DOWN        -> Hold
Exception + PREVENT -> Wait성 진행불가
DOWN + PREVENT      -> 설비
```

`Low WT 전체 = Hold + Wait성 진행불가 + 설비 + TIP + 기타` 가 항상 성립한다.
기타가 0 이면 화면에서 숨긴다.

#### Drill-down

LOT 상세는 **하나의 형식**으로 통일한다. 진입 경로만 다르고 표는 같다.

| 진입 | 조건 |
|---|---|
| 현황 카드의 Low WT 숫자 | 최신 업무일 + WT 구간 + 원인 (+ 전체/shift) |
| 추이 FlowStack 의 일별 지점 | 그 업무일 + 라인 (+ 패널에 따른 lot_status) |

`HOLD율` 패널을 누르면 `lot_status='HOLD'`, `WAIT성 진행불가율` 패널을 누르면
`WAIT(진행불가)` 로 걸러진다. 월/주 버킷은 특정 스냅샷이 없으므로 클릭해도
열리지 않는다.

표는 본문 우측 영역에 표시되며 별도 페이지로 이동하지 않는다.
내보내는 컬럼은 `f3_history` 에 실제로 있는 것만 쓴다. 원본에 `last_tkout_date`
컬럼이 없으므로 대신 `마지막이벤트경과_일` / `스텝도착경과_일` 을 보여준다.

### W/T 0 재공 분포

W/T = 0 인 재공만 **마지막 작업 이후 경과일**(`마지막작업경과_일`, `last_tkout_date`
기준)로 나눈다. MOVE 이력을 다시 뒤질 필요가 없다.

```
1일 이하 · 2일 이하 · 3일 이하 · 4일 이하 · 5일 이하 · 7일 이하 · 15일 이하 · 15일 초과
```

`2일 이하` = **1일 초과 ~ 2일 이하**. 오래 방치될수록 진하게 표시한다.

### 화면 배치 (/main/)

```
좌 summary                    우
  재공 뷰                       원인 분석 (대분류 3개 차트)
  status 뷰                       Hold | Wait성 진행불가 | Bottleneck
  W/T 분포                      드릴다운 (LOT 상세)
  W/T 0 재공 분포
```

원인 분석은 **대분류마다 별도 차트**다. 각 차트에서 중분류 -> 소분류로 파고들고,
말단에서 아래 드릴다운으로 이어진다.

### FlowStack 패널 순서

blueprint 7.1 기준, 위에서부터

```
MOVE  →  W/T  →  재공  →  HOLD율  →  WAIT성 진행불가율
```

x축은 다섯 패널이 완전히 공유하며 `[3개월][4주][7일]` 을 기본으로 한다.
Y축은 지표별 독립, 이중 Y축은 쓰지 않는다.

### 주(week) 기준

**일요일 ~ 토요일**이 한 주다. 주 번호는 `W##` 로 표기한다.

## 9. 결측 처리
