# Fab Flow Monitor — 공용 규칙

이 문서는 `build_f3.py`, `get_move.py`, 웹 사이트 전반에 **공통으로 적용되는 정의**를
모아둔 것이다. 새 지표나 화면을 만들 때 여기 정의를 그대로 따른다.

---

## 1. 업무일 (biz_date)

Fab 의 하루는 **22:00 시작 ~ 다음날 22:00 종료** 다.

```
2026-08-10 22:00:00  이상  ~  2026-08-11 22:00:00  미만   →  biz_date = 2026-08-11
```

즉 실행 시각이 22:00 이상이면 **다음 날짜**, 미만이면 **당일 날짜**가 업무일이다.

```python
def biz_date(ts):
    return (ts + timedelta(days=1)).date() if ts.hour >= 22 else ts.date()
```

## 2. Shift

| Shift | 기준 시각 | 구간 | 비고 |
|---|---|---|---|
| `GY` | 22:00 | 22:00 ~ 06:00 | **업무일의 첫 shift** |
| `DAY` | 06:00 | 06:00 ~ 14:00 | |
| `SW` | 14:00 | 14:00 ~ 22:00 | 업무일의 마지막 shift |

`biz_date = 2026-08-11` 의 shift 순서는 다음과 같다.

```
GY  (08-10 22:00)  →  DAY (08-11 06:00)  →  SW (08-11 14:00)
```

### 하루의 대표값

특별히 shift 를 지정해 조회하지 않는 한, **하루의 대표 표현은 `GY`(22:00) 데이터**다.

### Shift 배정 규칙 (스냅샷 적재)

스케줄러 실행 시각은 기준 시각과 정확히 일치하지 않는다. 그래서 **기준 시각에
가장 가까운 스냅샷**을 그 shift 의 데이터로 삼는다.

- 실시간 테이블은 **최근 2벌**의 스냅샷을 보관한다 (화면에는 최신 1벌만 노출).
- 매 실행마다 직전 shift 기준 시각과의 시간차(`dist_sec`)를 계산해,
  기존에 적재된 것보다 **더 가까운 스냅샷이면 교체**한다.
- 예) 21:50 실행 후 22:50 실행 → 22:00 기준으로 21:50(10분)이 22:50(50분)보다
  가까우므로 21:50 스냅샷이 `GY` 로 남는다.
- 스냅샷의 shift 라벨은 **그 shift 가 시작되는 시점** 기준이다.
  22:00 스냅샷 = 다음 업무일의 `GY`, 06:00 = `DAY`, 14:00 = `SW`.

이 방식은 다음 실행 시각을 몰라도 되고, 몇 번을 재실행해도 결과가 같다(멱등).

## 3. MOVE

### 정의

**MOVE = TrackOut 된 wafer 매수(qty)**. 건수가 아니라 매수다.

### 대상 Lot Type

```
lot_type IN ('PP', 'PB', 'PG')
```

이 세 종류만 생산성으로 인정한다. **다른 lot type 은 MOVE 에서 제외**한다.

### 집계 구간

`build_f3.py` 의 스냅샷 적재 시각을 `n` 이라 할 때,

| 단위 | 구간 |
|---|---|
| Shift | 그 shift 의 **실제 근무 구간** (GY 22~06, DAY 06~14, SW 14~22) |
| 일 | 업무일 전체 22:00~22:00 (= 3개 shift 의 합) |

### 스냅샷과 MOVE 의 짝 (W/T 계산)

f3 스냅샷과 MOVE 는 **같은 `(업무일, shift)` 라벨끼리 그대로 짝**이 된다.

| shift | f3 스냅샷 시각 (재공) | MOVE 구간 |
|---|---|---|
| `GY` | `(D-1) 22:00` | `(D-1) 22:00 ~ D 06:00` |
| `DAY` | `D 06:00` | `D 06:00 ~ D 14:00` |
| `SW` | `D 14:00` | `D 14:00 ~ D 22:00` |

```
W/T(D, S) = MOVE(D, S) ÷ 재공(D, S 스냅샷)
```

**분모는 그 조가 시작할 때의 재공, 분자는 그 조가 낸 MOVE** 다.
스냅샷은 shift 가 시작되는 시점으로 라벨링한다(`db_common.snapshot_shift`).

일 단위는 `(D, GY)` 스냅샷(= `(D-1) 22:00`, 업무일 시작 재공)과
업무일 `D` 전체 MOVE 를 쓴다.

적재 초기처럼 그 업무일에 `GY` 가 아직 없으면 **`DAY` → `SW` 순으로 대체**한다.
없는 날을 통째로 비우는 것보다 낫다.

## 4. W/T (WIP Turn)

```
W/T = MOVE(매) ÷ 재공(매)
```

**분모의 재공도 `lot_type IN ('PP','PB','PG')` 의 매수만 센다.** MOVE 가 특정
lot type 에 한정된 지표이므로 분모도 같은 모집단이어야 한다.

### 예시

20매짜리 LOT 이 하루에 48 MOVE 를 냈다면

```
W/T = 48 / 20 = 2.4
```

### Line 단위

```
LINE W/T = LINE 전체 MOVE ÷ LINE 전체 재공(매)
```

lot 별 W/T 의 평균이 **아니다**. 분자·분모를 각각 합산한 뒤 나눈다.

### 분자·분모의 시간 정합

W/T 의 분모(재공)는 스냅샷 시점 값이고 분자(MOVE)는 구간 누적이다.
**스냅샷 시각 `n` 과 MOVE 구간의 끝이 일치**해야 한다.

- Shift W/T : 분모 = `n` 시점 재공, 분자 = `n-8h ~ n` MOVE
- 일 W/T : 분모 = `n` 시점 재공, 분자 = `n-24h ~ n` MOVE

## 5. 테이블 구성

| 테이블 | 용도 | 갱신 방식 |
|---|---|---|
| `f3_live` | 웹 실시간 상세. 최근 2벌 스냅샷 | 매 실행 시 추가, 2벌 초과분 삭제 |
| `f3_history` | shift 단위 누적 상세 | shift 기준 시각에 가장 가까운 스냅샷으로 교체 |

웹은 실시간 조회 시 `f3_live` 의 최신 스냅샷을, 과거 조회 시 `f3_history` 를 본다.

| `PFR1_KFR7_MATERIALWORKSTATUS` | 〃 |

적재는 `getdata/spotfire_s3_export.py` 를 Spotfire 데이터 함수로 등록해 처리한다
(Tools > Register Data Functions, Refresh = Automatic). 분석 파일이 열려 데이터가

**주의**: 클라우드(웹) Spotfire 는 서버 Python 을 쓰므로 로컬에 설치한 boto3 가
잡히지 않는다. Spotfire Analyst(설치형)에서 실행해야 한다.

### S3 -> python

`getdata/s3_source.py` 가 S3 의 pkl 을 읽어 DataFrame 으로 돌려준다.
파일로 내려받지 않고 `get_object` + `io.BytesIO` 로 메모리에서 바로 읽는다.
**raw 자체는 DB 에 넣지 않는다.** bdq 로 받던 자리를 그대로 대체할 뿐이고,
DB 에 적재되는 것은 전처리 결과(f3, move)뿐이다.

```
python getdata/s3_source.py --list      S3 오브젝트 목록
python getdata/s3_source.py --peek LOT  한 테이블 미리보기
python getdata/s3_source.py --check     8개 전부 읽어 행수/컬럼 점검
```

Oracle 은 컬럼을 대문자로 주므로 읽는 즉시 소문자로 통일한다
(`LOWER_COLUMNS`). 이후 전처리는 기존 코드 그대로다.

### 원천 전환 스위치

`build_f3.py` / `get_move.py` 상단의 `SOURCE` 한 줄로 바꾼다.

```python
SOURCE = "s3"      # Spotfire 가 올린 raw (현행)
SOURCE = "bdq"     # 기존 bigdataquery 로 Impala 직접 조회 (폴백)
```

전처리·적재·웹은 양쪽이 완전히 동일하다. 바뀌는 것은 원천을 어디서 받느냐뿐이다.

S3 경로에서 달라지는 점 세 가지:
- `fa_object4` 는 datasource 가 달라 별도 파일로 오므로 `(line, lot_id)` 로 붙인다
- `STEP_PATH` / `TIP` 은 두 라인이 한 파일이라 `line` 으로 나눠 쓴다(파일은 1회만 읽음)
- `hold` 는 Oracle 쿼리에서 최신 `version_desc` 선별까지 끝나 별도 조회가 없다

## 6. 적재 주기

| 스크립트 | 주기 | 비고 |
|---|---|---|
| `getdata/build_f3.py` | **22:00 시작, 2시간 간격** | 실시간 갱신 + 06/14/22시분이 shift 로 누적됨 |
| `getdata/get_move.py` | **2시간마다 (build_f3 과 함께)** | 최초 3개월치, 이후 최근 20시간 |

스케줄러에는 `scripts/run_pipeline.bat` **하나만** 등록한다. 이 래퍼가 실행 시각을
보고 shift 기준시각(06/14/22시)일 때 `get_move.py` 까지 이어 돌린다.
`.bat` 은 반드시 작업 스케줄러에 등록해야 동작한다
(자세한 내용은 `docs/scheduler_guide.md`).

`getdata/db_common.py` 는 **실행 대상이 아니다.** 두 스크립트가 함께 쓰는
공용 라이브러리(접속·스키마·업무일/shift 계산·적재)이므로 스케줄러에 등록하지 않는다.

### Windows 작업 스케줄러 설정

작업 폴더를 지정하지 않으면 `C:\Windows\System32` 에서 실행되어 `.env` 와
상대경로가 어긋난다. `scripts/*.bat` 래퍼를 통해 실행한다.

**등록할 작업은 `run_pipeline.bat` 하나뿐이다.** 그 안에서 build_f3 -> get_move
순서로 돈다. 자세한 절차는 `docs/scheduler_guide.md`.

| 항목 | 값 |
|---|---|
| 프로그램 | `scripts\run_pipeline.bat` |
| 시작 위치 | 프로젝트 루트 |
| 트리거 | 매일 22:00 시작, **30분 간격** 반복, 기간 1일 |
| 옵션 | "작업이 이미 실행 중이면 새 인스턴스 시작 안 함" |

`snapshot_at` 은 **원천 조회를 시작한 시각**으로 기록된다. 따라서 정각에 시작하면
스냅샷도 정각으로 남아 shift 기준시각과 정확히 맞는다.

### 저빈도 테이블 캐시

설비그룹(`SMIMES_MI_EQP_GROUP_LIST`)처럼 하루에 한 번만 바뀌면 충분한 테이블은
**업무일(22시 기준) 단위로 로컬 캐시**한다. `getdata/cache/<name>_<YYYYMMDD>.csv`

- `'OFF'` 설비 제외까지 마친 상태로 저장한다
- 같은 업무일 안에서는 파일에서 읽고, 날짜가 바뀌면 새로 조회한다
- 이전 날짜 캐시는 자동 삭제된다

2시간 간격 실행 기준 하루 12회 중 1회만 실제 조회한다.

### MOVE 초기 적재 범위

3개월 전 날짜가 속한 **달의 1일**부터 채운다.

```
오늘 2026-08-10  →  3개월 전 2026-05-10  →  적재 시작일 2026-05-01
```

### MOVE 증분 적재

2시간마다 돌면서 **최근 20시간**을 받는다. 진행 중인 shift(최대 8h)와 직전
shift(8h)를 덮고도 여유가 있어, 실행이 몇 시간 밀려도 공백이 생기지 않는다.

조회 구간의 시작은 그 시각이 속한 **shift 시작 시각으로 정렬**해 구간이 경계에서
잘리지 않게 한다. 끝은 '지금' 이라 진행 중인 shift 도 부분 집계되며, 다음 실행에서
그 shift 전체로 교체된다.

교체 단위는 **(업무일, shift) 쌍**이다. 업무일 통째로 지우면 같은 업무일의 이미
적재된 다른 shift 가 날아간다. `f3_move_daily` 는 교체 후 `f3_move_shift` 에서 다시
합산해 만든다.

## 7. 차트 규칙

### 시각 속성 (blueprint 준수)

| 속성 | 의미 |
|---|---|
| 색 | **Line** |
| 선 종류 | Lot Type |
| 위치(패널) | 지표 |

Line 간 비교가 설계의 핵심이므로, **모든 차트는 Line 별로 구분해 그린다.**

### MOVE 차트 x축

```
[ 6월  7월  8월 ] │ [ W30  W31  W32  W33 ] │ [ 8/4 8/5 8/6 8/7 8/8 8/9 8/10 ]
     3개월              4주                        7일
```

- **당월·당주 포함**. 진행 중인 구간도 그린다.
- 단위가 바뀌는 지점에 **간극(gap)** 을 둬 구분한다.
- 최근 7일은 당월·당주에도 포함되지만 그대로 둔다. 일별 값을 개별로 보기 위함이다.
- **월/주 값 = 그 기간에 속한 일별 값의 평균** (총합 ÷ 일수가 아님)
  - W/T 도 마찬가지다. 총MOVE/총재공이 아니라 **일별 W/T 의 평균**이다.

### HOLD율 / WAIT성 진행불가율의 분모

**기본은 매수(qty) 기준**이며, 화면 상단 토글로 **Lot 수 기준**으로 전환할 수 있다.

```
HOLD율(매수)  = HOLD 상태 Lot 의 매수 합 ÷ 전체 재공 매수
HOLD율(Lot수) = HOLD 상태 Lot 수      ÷ 전체 재공 Lot 수
```

두 값은 크게 다를 수 있다. 매수가 큰 Lot 이 몰려서 HOLD 면 매수 기준이 높게,
소량 Lot 이 여러 건 걸리면 Lot 수 기준이 높게 나온다.
**어느 기준으로 본 값인지 항상 함께 표기**한다(패널 헤더에 표시).

MOVE / W/T / 재공은 정의상 매수 기준이므로 토글의 영향을 받지 않는다.

### 출력 컬럼이 늘어났을 때

`SUMMARY_OUTPUT_COLUMNS` 에 컬럼을 추가하면 `f3_live` / `f3_history` 스키마도
따라가야 한다. `CREATE TABLE IF NOT EXISTS` 는 기존 테이블을 건드리지 않으므로
`db_common.add_missing_columns()` 가 `ALTER TABLE` 로 보강한다.

```
python getdata/db_common.py --init
```

기존 데이터는 그대로 두고 없는 컬럼만 추가된다(기존 행은 NULL).
수동으로 하려면 `getdata/migrate_add_columns.sql` 참조.

### 날짜 컬럼 타입

원천마다 타입이 다르다. Oracle 쿼리에서 `TO_DATE` 로 변환한 컬럼은 datetime 으로,
변환하지 않은 컬럼은 `'YYYYMMDD HHMMSS...'` 문자열로 온다.

python 은 **`db_common.to_datetime()`** 하나로 받는다. 이미 datetime 이면 그대로
두고, 문자열이면 숫자만 뽑아 14자리로 파싱한다(ISO 문자열도 폴백 처리).

```python
d["tkout_date"] = DB.to_datetime(d["tkout_date"])
```

DuckDB 쪽 `parsed_ts()` 도 `TRY_STRPTIME` + `TRY_CAST` 조합이라 양쪽을 받는다.
따라서 Oracle 쿼리에서 날짜 변환을 추가하거나 빼도 python 을 고칠 필요가 없다.

### MOVE 증분 조회 창

`get_move.py` 의 `INCREMENTAL_HOURS` 는 **1** 이다. 시작 시각이 shift 경계로
정렬되므로 실제 창은 **진행 중 shift 전체(최대 8시간)** 가 된다. 부분 집계가
남지 않으면서 조회량은 최소가 된다.

```
23:15 실행 -> 22:00 ~ 23:15   (1.2시간)
05:15 실행 -> 22:00 ~ 05:15   (7.2시간)
07:15 실행 -> 06:00 ~ 07:15   (1.2시간)
```

30분 주기로 바뀌기 전에는 20 이었다(매번 20시간치를 다시 읽었다).

기간을 강제로 넓히려면:

```
python getdata/get_move.py --hours 6
python getdata/get_move.py --days 3
python getdata/get_move.py --from 2026-08-01 --to 2026-08-10
python getdata/get_move.py --full
```

### AREA

| 첫 글자 | AREA | | 첫 글자 | AREA |

| E | ETCH | | D | DIFF |
| P | PHOTO | | W | CLN |

목록에 없는 글자는 비워 둔다. 매핑을 바꿀 때는 `AREA_MAP` 만 고친다.

### 원인 계층

```
Hold            > (사유)                      hold_reason / 기준정보 유형
Wait성 진행불가  > 예약제외·FTP·설비이슈·TIP·가상스텝 > (사유/설비명)
Bottleneck      > AREA                       > 설비명
```

Bottleneck 계층은 **AREA(공정 구역)** 를 중분류로 쓴다. AREA 가 없으면
`(미분류)` 로 묶는다. 예전에는 중분류 없이 설비 200여 개가 대분류 바로
아래에 붙어 다른 대분류와 깊이가 어긋났다.

후보 설비 중 일부만 막힌 경우(=호환설비이슈)도 같은 AREA 아래에 두고,
소분류를 **막힌 설비만**으로 좁힌다.

### 호환설비이슈 (부분 차단)

설비·챔버 후보 중 **일부만** DOWN/TIP 이면 아직 갈 길이 남아 있다.
진행불가가 아니라 `Wait / 호환설비이슈` 로 본다.

```
CHAM그룹  TBO403-1, TBO403-4
설비상태  DOWN: TBO403-1
TIP      PREVENT: TBO403-1
-> 상태 WAIT,  제약원인 'Wait / 호환설비이슈'   (TBO403-4 로 갈 수 있다)

CHAM그룹  TBO404-1        (후보가 그것뿐)
설비상태  DOWN: TBO404-1
-> 'Wait성 진행불가 / 설비이슈'
```

막힌 설비 이름은 `설비상태`/`TIP` 문구에서 뽑는다(`_blocked_eqps`).
`DOWN: 이름(경과일↑)` 형태라 `:` 앞과 `(` 뒤를 걷어낸다.
비교 기준은 `eqpgroup_cham` 이 있으면 그것, 없으면 `eqpgroup` 이다.

원인 분석 카드는 3칸이라 `Wait` 은 **Bottleneck 카드**에
`호환설비이슈` 중분류로 담는다.

### 가상스텝 판정

**상태도 `WAIT(진행불가)` 로 매긴다.** 실제 설비를 기다리는 게 아니라
진행이 막힌 것이므로 `WAIT` 로 두면 원인 분석과 어긋난다
(`f1_status_base` 의 CASE 에 조건이 있다).

이미 적재된 스냅샷은 `getdata/migrate_virtual_step_status.sql` 로 한 번
고친다.


`eqpgroup` / `eqpgroup_cham` / `recipe_id` / `ppid` / `step_seq` / `step_desc`
중 **하나라도 `WAIT` 을 포함하면 가상스텝**이다. 실제 설비를 기다리는 게
아니므로 Bottleneck 이 아니라 `Wait성 진행불가 > 가상스텝 대기` 로 간다.

설비그룹이 빠져 있어 Bottleneck 으로 새던 적이 있다. 컬럼을 추가할 때
이 목록도 함께 본다.

### 연속공정 스텝 펼치기

f3 는 lot 당 **현스텝 + 연속블록** 행을 갖는다. 드릴다운 표는
`GROUP BY lot_id` 로 lot 단위 한 줄만 보여주므로 **재공 수가 중복되지 않는다.**

스텝이 둘 이상인 lot 은 맨 앞에 `+` 가 붙고, 누르면
`/api/lot-steps/` 로 그 lot 의 전 스텝을 받아 아래에 펼친다.
펼친 행은 화면 표시용이라 집계에 들어가지 않는다
(TIP/설비 문제가 현스텝이 아닌 다른 스텝에 있을 때 확인용).

### SHIFT 추이 차트

원인 분석 **왼쪽의 별도 카드**. 두 가지 x축을 오간다.

| scope | x축 | 뒤로 |
|---|---|---|
| `day` (기본) | 그 날짜의 SHIFT + 현재 | -> `week` |
| `week` | 최근 7일 (날짜) | 원인 계층만 |

`week` 에서는 어느 SHIFT 를 볼지 `GY / DAY / SW` 토글로 고른다(기본 GY).
`◀ 뒤로` 는 원인 계층을 먼저 올라가고, 더 올라갈 게 없으면 일간 -> 주간으로
빠진다. 어느 쪽이든 라인의 점을 눌러 같은 방식으로 파고든다.

x축은 **시계 기준**으로 만든다. 적재가 안 된 구간도 자리를 비워 둔다
(Spotfire 가 멈춰 데이터가 없어도 날짜가 건너뛰지 않는다).

```
scope=day    그 업무일에서 이미 시작된 SHIFT + 현재(적재시각)
             09:40 이면 GY 22:00 · DAY 06:00 · 현재
scope=week   오늘까지 최근 7일. 빈 날은 0 으로 둔다
```

업무일 D 는 **D-1 22:00 ~ D 22:00** 이다(`_biz_today`, `_shifts_started`).

드릴 대상:

```
재공 막대(주간)   그 날짜의 SHIFT 추이로 이동
Hold+Wait성      둘을 합친 소분류 상위 5
Hold / Wait성    각자의 하위
```

점이 겹쳐 찍기 어려우면 **범례 글자**를 눌러도 같은 동작이다.
아직 도래하지 않은 SHIFT 는 빼고, `현재` 는 맨 뒤 고정이 아니라
비어 있는 자리에 놓인다.

```
막대  재공(매)
라인  Hold+Wait성 / Hold / Wait성 진행불가  비율(%)
```

라인을 클릭하면 파고든다.

```
Hold            -> Hold 소분류 상위 5
Wait성 진행불가  -> 예약제외 / 설비이슈 / TIP / 가상스텝 대기 / FTP
  설비이슈       -> 그 안의 설비 상위 5
```

범례 체크박스로 라인을 숨길 수 있다. `Hold+Wait성` 은 합계라 드릴 대상이 아니다.

### W/T 계산 (calc_wt)

```
W/T = 그 lot 의 당일 MOVE 매수 / 재공 매수
```

MOVE 는 **TrackOut 이 끝난 것만** 잡힌다. 그래서 방금 RUN 으로 들어간 lot 은
실제로는 진행 중인데 W/T=0 으로 보인다. 이 잡음을 걷어내려고
**MOVE 가 없는 RUN 은 한 스텝(=1.0)** 으로 본다.

```
MOVE 있음          -> 실제 값 (예: 48/12 = 4.0)
MOVE 없음 + RUN    -> 1.0      <- 진행 중
MOVE 없음 + WAIT   -> 0.0
MOVE 없음 + HOLD   -> 0.0
```

이렇게 해야 **W/T=0 이 '작업 없이 멈춰 있는 재공'** 만 남는다.
W/T 를 새로 계산하는 곳이 생기면 `calc_wt()` 를 쓴다.

### 날짜 / SHIFT 필터

`/main/` 좌측 최상단. 기본값은 **현재**(f3_live)다.
날짜는 캘린더(`<input type="date">`)로 고르고, 선택 가능 범위는
`f3_history` 에 있는 biz_date 로 제한된다. 비우면 현재로 돌아간다.

SHIFT 는 `GY (22:00) / SW (14:00) / DAY (06:00)` 가 **항상 보이고**,
그 날짜에 적재가 없는 것은 `· 없음` 으로 표시하며 고를 수 없다.
고르면 `f3_history` 에서 읽는다(`_summary_rows(biz_date=, shift=)`).

### 드릴다운 컬럼 프리셋

어떤 차트에서 들어왔는지에 따라 기본 컬럼과 순서가 다르다
(`DRILL_PRESETS`, `_preset_for`).

| 프리셋 | 진입 경로 |
|---|---|
| `type` | 재공 구성 막대 |
| `wait` | status WAIT · 원인분석 Bottleneck |
| `waitng` | status WAIT(진행불가) · 원인분석 Wait성 진행불가 |
| `hold` | status HOLD · 원인분석 Hold |
| `run` | status RUN |
| `wt` | W/T 분포 · W/T 0 재공 분포 |

프리셋에 없는 컬럼은 **체크가 꺼진 채로 시작**할 뿐 사라지지 않는다.
체크하면 서버에서 값을 받아 바로 볼 수 있다.

**컬럼 이름은 `LOT_DETAIL_COLS` 한 곳에서만 바꾼다.** 프리셋은 키만 나열하므로
이름을 고치면 모든 프리셋에 함께 적용된다.

### 드릴다운 컬럼 선별 전송

`/api/lots-live/` 는 `cols=` 로 받은 컬럼만 실어 보낸다. 화면에서 감춘 컬럼은
아예 전송하지 않아 응답이 크게 준다(실측 296KB -> 36KB).
`lot_id` 와 `wt` 는 정렬·식별에 쓰이므로 감춰도 항상 포함한다.
감췄던 컬럼을 다시 켜면 값이 없으므로 자동으로 다시 조회한다.

### 라인 분류 (dest_line_id)

KFR7 원천 테이블에 **NRD-K 와 NRD 가 함께** 들어온다.
`smimes.mi_current_wip_v` 의 `dest_line_id` 로 가른다.

| 원천 line | dest_line_id | 최종 line |
|---|---|---|
| KFR7 | KFR7A, KFR7B | KFR7 (NRD-K) |
| KFR7 | KFR7C, KFR7D | **KFR4 (NRD)** |
| KFR7 | 그 외 | KFR7 (기존 분류 유지) |

**조인·집계는 전부 원천 라인(KFR7)으로 끝내고, f3 완성 후 라벨만 바꾼다**
(`relabel_lines`). 중간에 나누면 step_path / tip / equipment 조인을 라인별로
다시 짜야 해서 복잡해지는데 결과는 같다.

`dest_line_id` 는 f3 출력 컬럼으로 남기고 드릴다운 표에도 보인다.
쓰임새는 라인 분류 하나뿐이지만, 왜 그 라인으로 갈렸는지 확인할 수 있어야 한다.

MOVE 는 라인을 보지 않는다. `f3_move_lot` 은 원천 라인으로 적재되어 f3 의 분류와
어긋나므로, W/T 계산은 **lot_id 로만** 연결한다(`_lot_move_map`).
MOVE 쪽 라인 분류 체계는 아직 정립 전이라 보류한다.

### HOLD 유형 (기준정보 f3_std_holdtype)

각 유형의 사유 컬럼에 `condition1~3` 이 **모두** 포함되면 `type_name` 으로
분류하고, 드릴다운의 `원인` 컬럼에 `Hold(품질검토)` 처럼 붙는다.

```
type = ALL          세 사유 컬럼을 모두 검사 (기본값, 빈 값이면 ALL 로 저장)
type = HOLD/FTP/예약제외   그 사유만 검사
line 이 비면 전 라인
```

동시에 걸리면 **HOLD > FTP > 예약제외** 순으로 하나만 쓴다.

계산은 **`build_f3` 가 미리 해서 `cause_detail` 컬럼에 저장**한다. 웹은 그 값을
그대로 읽어 매 요청 재계산을 피한다. 규칙을 방금 고쳐 아직 배치 전이면 웹이
그 자리에서 계산하므로 값이 비어 보이지 않는다.
`/master/` 의 **저장 + 지금 반영** 버튼은 현재 스냅샷의 `cause_detail` 만
다시 채워, 다음 배치를 기다리지 않고 확인할 수 있게 한다.
여러 규칙이 맞으면 **조건이 많은(구체적인) 규칙**이 이기고, 그래도 같으면
**저장 순서(id)** 가 앞선 것을 쓴다.

### 모듈 (기준정보 f3_std_module)

`/master/` 의 모듈설정으로 `module1` / `module2` 를 채운다(`attach_module`).

```
line / proc_id            일치 (빈 칸이면 와일드카드)
start_layer ~ end_layer   layer_id 가 이 범위 (경계 포함)
start_stepseq ~ end_stepseq  step_seq 가 이 범위
```

여러 규칙이 맞으면 **지정된 조건이 많은(구체적인) 행이 이긴다.**
`module2` 가 비어 있으면 `module1` 과 같은 값이 들어간다.

**범위 비교는 숫자로 한다.** f3 의 layer 는 `050` 처럼 0 이 채워져 오는데
기준정보에는 `50` 이나 `20` 으로 들어오는 일이 많다. 문자열로 비교하면
`'050' < '20'` 이 되어 어긋난다. 숫자로 못 바꾸는 값(예: `A10`)만 문자열로
비교한다.

```
layer 050,  범위 20~74   -> 포함
layer 100,  범위 20~74   -> 제외
layer 005,  범위 0~10    -> 포함
```

### 테이블 이름 규칙

`app_db` 에 여러 프로젝트의 테이블이 섞여 있다. **이 프로젝트 것은 모두
`f3_` 접두**를 붙인다. 새 테이블을 만들 때도 반드시 붙인다.

```
f3_live  f3_history  f3_history_meta  f3_load_log
f3_move_shift  f3_move_daily  f3_move_lot
f3_std_module  f3_std_holdtype  f3_cause_rules
```

목록은 `db_common.PROJECT_TABLES` 에 있다.
이름을 바꾼 이력은 `getdata/migrate_rename_tables.sql` 참조.

### 같은 값, 다른 이름 (PLAN = PROC_ID)

원천마다 이름만 다를 뿐 **모두 같은 값**이다.

```
proc  =  proc_id  =  plan  =  process  =  process_id
```

f3 는 `proc_id` 로 들고 있다. 기준정보 `f3_std_plan.plan` 도 이 값이고,
LOT BALANCE 의 PLAN 구분도 `proc_id` 를 쓴다.
TIP 원천의 `process` 를 step_path 의 `proc_id` 와 조인하는 것도 같은 이유다.

### 라인 요약 카드 (지금 이 라인의 문제)

카드 네 장. 각 카드가 제 계층으로 5순위까지.

```
LOT 제약     HOLD / 예약제외 / FTP  >  제품 > 모듈 > LAYER
             (모듈이 없으면 바로 LAYER)
Bottleneck   B/N > AREA > 설비ID    막힘 배지 / 순수 몰림 배지
설비 이슈     PM · DOWN · LOCAL > AREA > 설비ID
PREVENT      PREVENT > AREA > 설비ID
```

행을 누르면 **요약카드 전용 조건**(`x_prod` · `x_mod` · `x_area` · `x_eqp`)
으로 화면을 좁힌다. 최상단 필터(제품 · AREA)를 건드리면 요약카드 목록
자체가 바뀌어 다음 행을 고를 수 없으므로 따로 둔다.
**요약카드는 최상단 필터까지만 반영**하고 `x_*` 는 무시한다.


원인 분석 위에 4장. **매수 순**으로 세우고 그것이 만든 W/T 저해를 잇는다.

```
① Bottleneck > CVD        ▲ +2,100
   13,857 매        57%
   TCV401 4.2k매 · LAYER 110 · 제품 D1x
   W/T 0 6.5k매 · 평균 5.2일 정체 · 최장 11.0일
```

단위는 `대분류 > 중분류` 다. 그 안에서 가장 큰 소분류 · LAYER · 제품을
함께 보여 준다. 카드를 누르면 그 원인으로 화면 전체가 좁혀진다.

추세는 **전일 같은 SHIFT** 와 견준다(`f3_history`). 비교할 스냅샷이 없으면
`비교 없음` 으로 둔다.

정체는 **임의 기준일을 두지 않는다.** 매수로 이미 순위를 매겼으므로
평균 · 최장 정체일을 실측해 보여 준다.

### 드릴다운 계층 (중요)

위를 고르면 **아래는 모두 리셋**된다. 아래가 위를 바꾸지는 못한다.

| lv | 대상 |
|---|---|
| 1 | 좌측 최상단 필터 (날짜 · SHIFT · 라인 · 제품군 · 제품 · lot_type) |
| 2 | 좌측 차트 (재공막대 · status 원 · W/T 분포 · W/T 0 분포) |
| 3 | SHIFT 추이 (과거를 포함한 시계열이라 원인 분석보다 위다) |
| 4 | 원인 분석 |
| 5 | 원인 분석 전체보기 |
| 6 | LOT BALANCE |
| 7 | 드릴다운 표 |

누적막대는 **구간과 조각(status)을 한 번에** 건다. 이때만 같은 계층 정리를
건너뛴다(`setCond(..., keepPeers=true)`).

**같은 계층에서 다른 차트를 누르면 그것만 남기고 리셋**된다
(`dfClearPeers`). Ctrl 은 같은 차트 안에서만 여러 개다.
계층을 건너뛰어도 된다(1 고르고 4 를 고르면 2·3 은 무관하다).

코드에서는 `DF_LV` 로 계층을 매기고 `dfResetBelow(lv)` 가 아래를 지운다.
새 드릴다운 요소를 추가하면 **반드시 `DF_LV` 에 계층을 등록한다.**

다만 **요약카드 자체는 최상단 필터까지만** 반영한다.

### AND / OR 규칙 (중요)

조건은 **차트가 아니라 필드** 단위다. 차트가 달라도 같은 필드를 건드리면
같은 조건이다.

| 필드 | 어느 차트에서 걸리나 |
|---|---|
| `status` | 원차트 · W/T 0 조각 · LOT BALANCE 조각 |
| `wt0` | W/T 0 막대(경과기간) |
| `type` | 재공 막대 |
| `wt` | W/T 분포 |
| `layer` | LOT BALANCE 막대 |
| `cause` | 원인 분석 |

```
같은 필드의 여러 값   OR    상태 HOLD 또는 WAIT
서로 다른 필드끼리    AND   상태 HOLD  ·  W/T 0 2일 이하  ·  재공 PP
원인 분석의 다른 갈래  OR    Hold > FLOW금지 또는 Wait성 > 설비이슈
```

**같은 필드를 다른 차트에서 고르면 교집합**이다(`DF_SRC` 가 출처를 기억한다).

```
원차트에서 Ctrl 로 (진행불가 OR HOLD) 를 고른 뒤
W/T 0 에서 HOLD 조각을 고르면
  (진행불가 OR HOLD) AND HOLD = HOLD
-> 양쪽 차트 모두 HOLD 만 남는다
```

범위를 좁히려는 의도이므로 그 값만 남긴다. 해제는 **같은 차트에서 같은 값을
다시 누를 때만** 일어난다.

누적막대는 **구간과 조각을 한 쌍**으로 다룬다(W/T 0, LOT BALANCE).
구간이 같아도 조각이 다르면 다시 누른 것이 아니므로 해제하지 않는다.
`setCond(..., noToggle)` 가 이를 맡는다.

**조합 결과가 0 이면 0 을 그대로 보여 준다.** 한쪽을 자동으로 풀지 않는다.
사용자가 자기 선택이 잘못됐음을 알 수 있어야 한다
(예: `W/T 0<x≤1` + `W/T 0 2일 이하` 는 양립하지 않아 0 건이 맞다).

**같은 계층이라도 축이 다르면 함께 걸린다(AND).** 상태 HOLD 와
W/T 0 2일 이하는 양립하므로 서로를 지우지 않는다(`dfClearPeers` 는 비어 있다).
지우는 건 같은 축의 값뿐이고 그건 `setCond` 가 목록으로 처리한다.

조건 이름은 **`dfTitle` / `dfOneName` / `causeName` 세 함수에서만** 만든다.
표 제목·LOT BALANCE 경로·원인 분석 상단 모두 이 함수를 쓴다.
다른 곳에서 따로 조립하면 표기가 어긋난다(그래서 `wait > hold` 가 나왔다).

`DF_DEF` 의 `one: true` 가 단일값 조건임을 뜻한다. 지금은 전부 단일값이다.
새 조건을 추가할 때 **한 LOT 이 여러 값에 걸릴 수 있는지** 반드시 따져
`one` 을 정한다. 서버는 쉼표 목록을 `IN` 절로 받아 OR 로 처리한다.

표기도 같은 규칙을 따른다. 같은 축의 값은 `또는`, 다른 축은 `·`,
상위-하위 관계만 `>` 를 쓴다. 같은 계층을 `>` 로 잇지 않는다.

### LOT BALANCE

드릴다운 표 위, 추이/원인 분석 아래. x축은 LAYER, y축은 재공(LOT/매 토글,
기본 매). 드릴다운과 같은 조건을 쓴다.

막대는 **status 누적**이다(RUN 파랑 / WAIT 초록 / HOLD 빨강 /
WAIT(진행불가) 노랑 — 원차트와 같은 색).

접힌 상태는 **전체 합산 한 줄**이다. 버튼은 셋이다.

```
제품 펼치기   제품(prod2) 으로 나눔. 다시 누르면 목록에서 항목을 고른다
PLAN 펼치기   PLAN(proc_id) 으로 나눔. 메인 PLAN 은 ★ 로 먼저 나온다
접기          펼치기 자체를 해제하고 합산 한 줄로 돌아간다
```

둘 다 켜면 `제품 · PLAN` 으로 묶인다. 버튼을 눌러 축을 켜도 **바로 나뉘지
않고**, 목록에서 항목을 골라야 그 항목만 펼쳐진다. 하나도 안 고르면 합산
한 줄로 돌아가되 축 설정은 남는다.

x축 아래에는 **모듈 구간**이 선으로 나뉘고 가운데에 이름이 붙는다
(기준정보 모듈설정의 `module1`, 같은 값이 이어지는 구간을 묶는다).
**x축(LAYER)은 모든 PLAN 이 공유**해 없는 LAYER 는 빈칸으로 비운다.

```
LAYER   000  001  002  003  004
B(메인)  25    -   25   25   25
A        25   25    -   25    -
```

PLAN 은 `proc_id` 다. 맨 위에 오는 PLAN 은 기준정보 `f3_std_plan` 의
**메인체크**가 켜진 것이고, 여럿이면 PLAN 명 오름차순이다(`_main_plans`).

### 제품구분 (SSPS_PROD_NAME)

`PROD1` / `PROD2` / `DEPT` 를 lot 에 붙인다. 조인 키는 세 개다.

```
line = LINE_ID  AND  lot_type = LOT_TYPE  AND  LEFT(lot_id, LEN(ID)) = ID
```

`ID` 길이가 **2~4 로 제각각**이라 길이별로 나눠 붙이고, 같은 lot 에 여러 길이가
맞으면 **더 긴(구체적인) 규칙**을 쓴다(`attach_prod`).

`/main/` 좌측 **라인 토글 바로 아래**에 다중선택 필터가 있다.
화면 이름은 `PROD1` -> **제품군**, `PROD2` -> **제품** 이다.

목록 맨 위의 **ALL** 이 전체 선택 스위치다. 켜면 전부 선택, 끄면 전부 해제되고
기본값은 ALL 이다. 내부적으로는 *선택 없음 = 전체* 로 다루므로, 전부 선택된
상태에서는 서버에 빈 값을 보내 필터를 걸지 않는다.

제품군을 고르면 제품 선택지가 그에 맞게 좁혀진다. 필터는 모든 차트와
드릴다운 표에 함께 적용된다.

### 경과일 기준 시각 (중요)

DuckDB 의 `CURRENT_TIMESTAMP` 는 **UTC** 를 돌려준다. 원천 시각은 KST 라
그대로 빼면 최근 9시간 이내 값이 미래로 보여 **경과일이 음수**가 된다.

그래서 파이프라인 시작 시각(로컬, `snapshot_at` 과 동일)을 리터럴로 박아 쓴다.

```python
set_now(run_at)      # NOW_SQL = TIMESTAMP '2026-08-14 10:15:00'
```

원천에 미래 시각이 들어와도 음수가 나오지 않도록 `GREATEST(..., 0)` 도 건다.
새로 경과일 계산을 추가할 때는 `elapsed_days_num()` 을 쓰고
`CURRENT_TIMESTAMP` 를 직접 쓰지 않는다.

### 경과일 컬럼

f3 는 네 가지 경과일을 담는다. 모두 `현재시각 - 기준시각` 을 일 단위 소수 1자리로.

| 컬럼 | 기준 |
|---|---|
| `투입경과_일` | `start_date` |
| `마지막이벤트경과_일` | `last_event_date` |
| `스텝도착경과_일` | `step_arrive_date` |
| `마지막작업경과_일` | `last_tkout_date` (마지막 TrackOut) |

`마지막작업경과_일` 은 "실제로 설비를 마지막으로 빠져나온 뒤 얼마나 지났는가"라
정체 판정에 가장 직접적이다. 이벤트 경과는 상태 변경만으로도 갱신되므로 다르다.

### 표기 자릿수

| 지표 | 자릿수 |
|---|---|
| MOVE | 정수 |
| 재공 | 정수 |
| W/T | 소수 1자리 |
| HOLD율 / WAIT성 진행불가율 | 소수 1자리 (%) |

월/주 평균도 같은 자릿수로 맞춘다. 화면에는 산식을 표기하지 않는다.

### 차트 값 레이블

점 위에 값을 직접 표기한다. 좁은 패널에 맞춰 축약하되, **커서를 올리면 항상
원래 값**이 보인다.

| 지표 | 레이블 | 툴팁 |
|---|---|---|
| MOVE / 재공 | 1000 단위 + 소수 1자리 (`13.3k`) | `13,300 매` |
| W/T | 소수 1자리 (`2.4`) | `2.4 매/매` |
| HOLD율 / WAIT성 진행불가율 | 정수 (`33`) | `33.3 %` |

### FAB현황 summary 뷰 순서

```
라인 토글 (단일 선택, 기본 NRD-K)
  재공 뷰       LOT / 매 + lot_type 구성
  status 뷰     원차트 + 선택 정보
  W/T 분포 뷰   WT=0 이 맨 위, 아래로 갈수록 정상
  원인 분석 뷰   대분류 > 소분류
```

좌측이 summary(카드 1개 폭), 우측 나머지가 드릴다운이다.

### 원인 대분류 / 소분류

3단계다. 대분류 > 중분류 > 소분류. 겹치면 위에서부터 하나에만 귀속한다.

| 대분류 | 중분류 | 소분류 |
|---|---|---|
| Hold | — | hold 유형 (기준정보) |
| Wait성 진행불가 | 설비이슈 | EQP ID (상위 N) |
| | TIP | EQP ID (상위 N) |
| | FTP | FTP 유형 (기준정보) |
| | 예약제외 | 예약제외 유형 (기준정보) |
| | 가상스텝 대기 | — |
| Bottleneck | — | EQP ID (상위 N) |

- **Bottleneck** 은 `lot_status = 'WAIT'` 인 LOT 만 센다(진행은 가능하나 대기).
- **Hold** 는 `lot_status = 'HOLD'` 또는 hold 값이 있는 LOT.
- 소분류가 설비인 경우 설비그룹 n개면 각 설비에 `1/n` 로 나눠 계상한다.
- 화면은 **차트**로 파고들고, 말단에서 우측 **드릴다운 표**로 원자료를 본다.
  분류 로직(`classify_lot`)을 요약과 드릴다운이 공유해 값이 어긋나지 않는다.

**가상스텝 대기** = `recipe_id` / `step_seq` / `step_desc` 중 하나에 `WAIT` 이
포함된 LOT. Wait성 진행불가의 중분류다.

### lot_type 기본 선택

FAB현황의 lot_type 필터 기본값은 **PP + PG** 다. 사용자가 바꾸면 그 선택이
브라우저에 저장되어 라인이나 뷰를 바꿔도 유지된다.

hold / exception / ftp 의 유형은 아직 정립 전이라 `기준정보` 화면에서 키워드 →
유형 규칙을 등록해 쓴다. 규칙이 없으면 사유 원문이 그대로 유형이 된다.

### 화면 구성

```
┌──────────────────────────────────────────┐
│ 상단 메뉴바                                │
├──────────────────────────────────────────┤
│ 현황 카드  NRD │ NRD-P │ NRD-K │ NRD-V     │  ← 현재 단면(f3_live)
├──────────────────────────────────────────┤
│ FlowStack (추이)        │ 상세             │
└──────────────────────────────────────────┘
```

### 라인 표기

| 화면 표기 | 실제 코드 |
|---|---|
| NRD | KFR4 |
| NRD-P | PFR1 |
| NRD-K | KFR7 |
| NRD-V | KFR6 |

데이터가 없는 라인은 카드를 반투명 처리하고 가운데에 **개발중** 을 띄운다.

### lot_status 색

| 상태 | 색 |
|---|---|
| `RUN` | 파랑 `#2563EB` |
| `WAIT` | 초록 `#16A34A` |
| `HOLD` | 빨강 `#DC2626` |
| `WAIT(진행불가)` | 노랑 `#EAB308` |

도넛 가운데 기본값은 **HOLD + WAIT(진행불가)** 비율이다. 조각이나 범례를 누르면
그 상태의 `%` / `LOT 수` / `매수` 로 바뀌고, 다시 누르면 기본값으로 돌아온다.

### 대기 LOT 상위 설비 5

현스텝의 `eqpgroup` 을 설비 단위로 펼쳐, `lot_status` 가
`WAIT` 또는 `WAIT(진행불가)` 인 LOT 을 센다. `HOLD` 는 설비 대기가 아니므로 제외.

상위 5는 **기준(LOT / 매)마다 따로 뽑는다.** 소량 LOT 여러 건이 걸린 설비와
대량 LOT 소수가 걸린 설비는 순위가 뒤집히므로, 같은 5개를 재정렬하면 안 된다.
화면 기본값은 **매 기준**이다.

**설비그룹이 n개 설비로 엮여 있으면 각 설비에 `1/n` LOT, `1/n` 매로 나눠 계상한다.**
모든 설비에 1랏씩 계상하면 합계가 실제 대기량보다 부풀려진다.

```
25매 LOT 1건이 설비 4개 그룹에서 대기
  -> 설비당 0.25 LOT / 6.25 매
설비 1개 그룹이면
  -> 1.00 LOT / 25 매
```

### 카드의 lot_type 토글

카드 최상단에 **라인 전체 재공(LOT 수 / 매수)** 을 표기하고, 그 옆 토글로
lot_type 을 고른다. `전체` 가 기본이며 선택하면 **카드 전체**(재공 수치,
도넛, 상위 설비)가 해당 lot_type 기준으로 다시 그려진다.

### lot_type 정렬

```
PP → PB → PG → EG → (그 외 오름차순)
```

### Low WT 분석

WT 는 lot 단위로 계산한다. `f3_move_lot`(lot 단위 MOVE) ÷ 재공 매수.
**MOVE 기록이 없으면 WT = 0** 이다. `last_tkout_date` 는 쓰지 않는다
(WT=0 뿐 아니라 저조 WT 구간까지 봐야 하므로).

- 기준은 Dropdown 으로 고른다. 기본 `WT = 0`, 그 외 `WT ≤ 0.5`, `WT ≤ 1.0`
- 기준을 넓혀도 **구간은 합치지 않는다**: `WT=0` / `0<WT≤0.5` / `0.5<WT≤1.0`
- 열은 `전체 | GY | DAY | SW`. **전체는 shift 합이 아니라 unique lot** 기준
  (업무일 대표 스냅샷의 lot + 하루 전체 MOVE)
- Lot 수와 **Low WT율**(분모 = 그 구간의 분석 대상 lot)을 함께 표시

#### 원인 대분류와 우선순위

겹치면 **위에서부터 하나에만** 귀속한다. 중복 카운트 없음.

| 순위 | 대분류 | 판정 |
|---|---|---|
| 1 | Hold | `hold` 값 존재 |
| 2 | Wait성 진행불가 | `exception` 또는 `ftp` 존재 |
| 3 | 설비 | `down` 존재 (DOWN / PM / LOCAL) |
| 4 | TIP | `tip` 존재 (PREVENT) |
| 5 | 기타/미분류 | 위 어디에도 없음 |

```
Hold + DOWN        -> Hold
Exception + PREVENT -> Wait성 진행불가
DOWN + PREVENT      -> 설비
```

`Low WT 전체 = Hold + Wait성 진행불가 + 설비 + TIP + 기타` 가 항상 성립한다.
기타가 0 이면 화면에서 숨긴다.

#### Drill-down

LOT 상세는 **하나의 형식**으로 통일한다. 진입 경로만 다르고 표는 같다.

| 진입 | 조건 |
|---|---|
| 현황 카드의 Low WT 숫자 | 최신 업무일 + WT 구간 + 원인 (+ 전체/shift) |
| 추이 FlowStack 의 일별 지점 | 그 업무일 + 라인 (+ 패널에 따른 lot_status) |

`HOLD율` 패널을 누르면 `lot_status='HOLD'`, `WAIT성 진행불가율` 패널을 누르면
`WAIT(진행불가)` 로 걸러진다. 월/주 버킷은 특정 스냅샷이 없으므로 클릭해도
열리지 않는다.

표는 본문 우측 영역에 표시되며 별도 페이지로 이동하지 않는다.
내보내는 컬럼은 `f3_history` 에 실제로 있는 것만 쓴다. 원본에 `last_tkout_date`
컬럼이 없으므로 대신 `마지막이벤트경과_일` / `스텝도착경과_일` 을 보여준다.

### W/T 0 재공 분포

W/T = 0 인 재공만 **마지막 작업 이후 경과일**(`마지막작업경과_일`, `last_tkout_date`
기준)로 나눈다. MOVE 이력을 다시 뒤질 필요가 없다.

```
1일 이하 · 2일 이하 · 3일 이하 · 4일 이하 · 5일 이하 · 7일 이하 · 15일 이하 · 15일 초과
```

`2일 이하` = **1일 초과 ~ 2일 이하**. 오래 방치될수록 진하게 표시한다.

### 화면 배치 (/main/)

```
좌 summary                    우
  재공 뷰                       원인 분석 (대분류 3개 차트)
  status 뷰                       Hold | Wait성 진행불가 | Bottleneck
  W/T 분포                      드릴다운 (LOT 상세)
  W/T 0 재공 분포
```

원인 분석은 **대분류마다 별도 차트**다. 각 차트에서 중분류 -> 소분류로 파고들고,
말단에서 아래 드릴다운으로 이어진다.

### FlowStack 패널 순서

blueprint 7.1 기준, 위에서부터

```
MOVE  →  W/T  →  재공  →  HOLD율  →  WAIT성 진행불가율
```

x축은 다섯 패널이 완전히 공유하며 `[3개월][4주][7일]` 을 기본으로 한다.
Y축은 지표별 독립, 이중 Y축은 쓰지 않는다.

### 주(week) 기준

**일요일 ~ 토요일**이 한 주다. 주 번호는 `W##` 로 표기한다.

## 9. 결측 처리

**결측일은 존재하면 안 된다.** 스케줄러가 실패하면 해당 업무일을 다시 실행해
채운다. 월/주 평균이 기간 나눗셈이므로 결측이 있으면 값이 낮게 왜곡된다.

`f3_history_meta` 와 `f3_move_daily` 의 `biz_date` 연속성을 주기적으로 점검한다.
